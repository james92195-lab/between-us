# Host Between Us on Render

The signed-in app (accounts, shared circles, and the 3-friend jar vote) runs as a Node server with Postgres. GitHub Pages stays the static notebook at [james92195-lab.github.io/between-us](https://james92195-lab.github.io/between-us/). This file is the Render setup. It does not move money. Dwolla stays off.

## What you click

1. Sign in to [Render](https://render.com) with GitHub.
2. Choose **New**, then **Blueprint**.
3. Pick the GitHub repo **james92195-lab/between-us**.
4. Click **Apply**.

Render reads `render.yaml` from the default branch (`main`). After this change is on `main`, the same setup is one link:

[https://render.com/deploy?repo=https://github.com/james92195-lab/between-us](https://render.com/deploy?repo=https://github.com/james92195-lab/between-us)

That link applies only once `render.yaml` is on `main`. Before that, use **New > Blueprint**, pick this repo, and select the branch that contains the file.

## The URL you get

The web service is named `between-us`. Render serves it at:

`https://between-us.onrender.com`

If that name is already taken, Render assigns a different `onrender.com` host. The dashboard shows the real URL after Apply. Render sets `RENDER_EXTERNAL_URL` to that address. The Blueprint copies it to `BETTER_AUTH_URL`. If that copy is empty, the server uses `RENDER_EXTERNAL_URL` for the sign-in origin, trusted origins, and CORS. The site is at `/`, not under `/between-us/` (that path is GitHub Pages only).

Open that URL, create an account, and invite the other three people by the email they used to sign up. A jar withdrawal still needs yeses from three other active members. Three yeses do not send money.

## What the Blueprint creates

- A Node web service on the **free** instance (0.1 CPU, 512 MB). It builds with `npm ci && npm run build:render`. The start command is `npm run db:migrate && npm start`. `npm start` migrates again, then listens. Applied SQL files are recorded in `_migrations`, so a second run does nothing. Render’s pre-deploy command is only for paid web services, private services, and background workers, so this free service does not set `preDeployCommand`.
- Node is pinned with `NODE_VERSION=22`. A service created now otherwise defaults to Node 24. `HOST` is `0.0.0.0`, which is the host Render requires. `PORT` is not set in the Blueprint. Render injects it (default `10000`), and the server binds that value.
- A Render Postgres database named `between-us-db` on the **free** plan (Postgres 16, database `between_us`). `DATABASE_URL` is the internal connection string. No password is stored in the repo. `BETTER_AUTH_SECRET` is generated by Render (`generateValue: true`). `BETTER_AUTH_URL` is a copy of the platform variable `RENDER_EXTERNAL_URL`. Render’s Blueprint spec allows that self-reference. The server still reads `RENDER_EXTERNAL_URL` when the copy is missing.

Free web services spin down after about 15 minutes without traffic. The next visit waits through a cold start.

### Free Postgres expiry

Render’s free database is temporary:

- It **expires 30 days after creation**.
- You then have a **14-day grace period** to upgrade to a paid plan.
- After the grace period Render **deletes the database and its data**.
- The free plan is 1 GB, has no backups, and is limited to one free database per workspace. It can restart and drop connections.

When it expires, accounts and circles on that database are gone. Export anything you need before the grace period ends, or upgrade the database in the Render dashboard. The free web service does not keep the data by itself.

## Transfers stay off

These variables are declared and left empty: `DWOLLA_ENVIRONMENT`, `DWOLLA_CLIENT_ID`, `DWOLLA_CLIENT_SECRET`, `DWOLLA_WEBHOOK_SECRET`, `DWOLLA_PLAID_EXCHANGE_PARTNER_HREF`, `DWOLLA_P2P_APPROVAL`, `DWOLLA_LAUNCH_COUNTRY`, `DWOLLA_SANDBOX_DISPATCH`.

Empty means the server will not call Dwolla. Do not paste keys into the Blueprint or the dashboard. Confirmed jar funds stay `$0`. A policy-approved withdrawal is not a payment.
